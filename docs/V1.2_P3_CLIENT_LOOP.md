---

## 0. 一句话目标

在真实 Control UI 里，从一次聊天请求开始，完成：

**Job → Patch → Sandbox → Repair Worker → 新 Patch → 复测 → 结果展示**

全程不离开客户端，不需要手工敲 CLI；所有执行仍以 Owner 的批准与哈希为准。

---

## 1. 现状与差距

v1.1 已具备（客户端 PoC 验收通过）：

| 能力 | 现状 |
| --- | --- |
| Owner 页面 | OpenClaw 原生插件页，展示 Job / Patch / Sandbox / Repair |
| Job | 聊天工具 `owner_job_submit` 创建；UI 审批 |
| Patch | UI 查看冻结 Diff；approve / apply 分离 |
| Sandbox | UI 创建、审批；真实 Docker 执行（通过 CLI/seed） |
| Repair | UI 审批已冻结的 cycle |
| 更新 | 手动 Refresh |

缺口（决定了下一阶段的范围）：

1. **执行不在客户端闭环**：`run-once`、`sandbox-run-once` 仍靠 CLI；UI 批准后没有 Worker 接手。
2. **Repair 入口缺失**：失败 Sandbox → 创建 Repair cycle 目前只在 seed/CLI 里有。
3. **没有进度与结果**：Worker 运行中、测试日志、最终 `tested_pass` 都看不到。
4. **没有 Repair 后的新补丁流程**：批准 cycle 只创建 repair Job，后续 Patch/复测没有串起来。
5. **没有聊天内结果卡片**：结论只在独立页面。

## 2. 目标用户旅程（P3）

```
[Chat] 用户: 修复 retry 的失败测试
   │  （模型调用 owner_job_submit，或 UI「New job」）
   ▼
Job(pending) ──UI 审批──► Job(queued)
   │  Worker 生成补丁
   ▼
Patch(proposed) ──UI 查看 Diff + 审批──► approved ──UI 应用──► applied
   │
   ▼
Sandbox(pending) ──UI 审批──► Docker 运行 ──► completed/fail
   │
   ▼
 Repair(pending) ──UI 审批──► Repair Worker 生成新补丁
   │
   ▼
Patch(repair, proposed) ──UI 审批/应用──► applied
   │
   ▼
Sandbox(repair) ──UI 审批──► Docker 复测 ──► completed/pass
   │
   ▼
结果页 / 聊天卡片：tested_pass + Diff + 测试输出 + 时间线
```

关键不变量：

- Worker 只执行**已批准**的 Job / Sandbox / Repair；没有任何自动批准。
- 批准仍绑定冻结哈希；UI 仍是唯一产生审批的动作入口。
- 不自动 commit / push / merge，不改 OwnerTask。

## 3. 架构

```
┌──────────────── OpenClaw（原版，复用）────────────────┐
│ Control UI（原生页面 / 聊天 / 通知）                    │
│   └─ owner-agent 插件                                  │
│        ├─ 只读查询：status / job / patch / sandbox …    │
│        ├─ UI 动作：审批、应用、创建 Sandbox/Repair       │
│        └─ 轮询或 feature 事件：进度与结果               │
└───────────────────────┬───────────────────────────────┘
                        │ loopback HTTP（读取/审批令牌）
┌───────────────────────▼───────────────────────────────┐
│ Owner sidecar（本仓库）                                │
│  ├─ HTTP API（现有）                                    │
│  ├─ Worker loop（新增）                                 │
│  │    ├─ PatchCodingWorker（普通/修复 Job）             │
│  │    └─ SandboxRunner（已批准的 Run）                  │
│  └─ OwnerStore（唯一权威）                              │
└───────────────────────────────────────────────────────┘
```

**新增的只有 Worker loop 与少量 UI 入口**；不新建 Gateway、不新建会话层、不重写聊天。

## 4. 复用清单（OpenClaw 原生优先）

| 需求 | 复用 | 不自研 |
| --- | --- | --- |
| 页面 / 导航 / 对话框 | Control UI `registerPage` / `registerNavigation` / 原生 `<dialog>` | 不写新 SPA |
| 聊天与会话 | Gateway session / transcript / composer | 不写聊天层 |
| 通知 | 浏览器推送 / `plugin.approval` 或 attention 分类 | 不写推送服务 |
| 事件与订阅 | `defineFeatureContract.events` + `feature.watch`（Phase 2） | 不写 WebSocket |
| Markdown / 终端输出 | Control UI 渲染器（Phase 2 可嵌入） | 不写渲染器 |
| 桌面 | 官方 Tauri / macOS / Windows Hub | 不自建壳 |

## 5. 分阶段交付

### Phase P3.1：手动推进（1–2 天）

目标：把现有 Worker 接到 UI，先跑通完整链路。

| 工作项 | 位置 | 说明 |
| --- | --- | --- |
| `ownerctl worker --once` / `serve --worker` | `bin/ownerctl.mjs` | 复用 `PatchCodingWorker` + `SandboxRunner`，只处理 queued/approved |
| `POST /owner/v1/worker/tick` | `src/sidecar-server.mjs` | UI 触发一次推进（审批令牌保护） |
| `GET /owner/v1/worker/status` | 同上 | 当前可执行项、最近一次结果 |
| Repair 入口 | sidecar + 插件 | 从 `completed/fail` 的 Sandbox 创建 cycle |
| UI「Advance」/「Run next step」 | 插件页面 | 审批后手动推进，避免常驻进程 |
| 轮询 | 插件页面 | 有活动任务时 2s 刷新，空闲时停止 |
| E2E | `scripts/e2e/` | 从空库开始，用 Fake agent 跑完整链路 |

验收：

- 空 Owner 库 + 一次 UI/聊天操作，能完成 Job → Patch → Sandbox(fail) → Repair → Patch → Sandbox(pass)。
- 最终 `repair.status = tested_pass`，UI 显示测试输出与 Diff。
- 审批前 Worker 不得执行；拒绝/过期 fail closed。

### Phase P3.2：自动推进 + 事件（2–3 天）

- 常驻 Worker（`ownerctl serve --worker`），带租约/心跳/优雅退出。
- 插件通过 `feature.watch` 订阅 Owner 事件；sidecar 提供变更通知（轻量 SSE 或事件轮询）。
- 聊天内嵌结果卡片（`registerInlineView`）：一次 Job/Cycle 的摘要与最终状态。
- 通知：审批待办、修复完成/失败。

验收：

- UI 不再需要手动 Refresh；进度与结果自动出现。
- 断线重连后能恢复当前状态（`feature.watch` 的重新快照）。

### Phase P3.3：结果与恢复（1–2 天）

- Cycle 时间线：Job → Proposal → Sandbox → Repair → 复测，含哈希与时间。
- 测试输出查看器（截断 + 脱敏）。
- 取消、重试、对账（复用现有 `reconcile` / `recover`）。
- 错误 UX：失败原因、下一步动作、重试入口。

## 6. 关键设计决策

1. **Worker 属于 Owner，不属于 OpenClaw**：继续由 sidecar 执行，保持审批与沙箱边界。
2. **UI 动作只做“推进”，不做“自动循环”**：P3.1 每次只推进一个已批准步骤，避免隐式自动化。
3. **轮询优先于事件**：先 2s 轮询跑通体验，再用 `feature.watch` 替换；不写新的 WS 层。
4. **结果展示复用现有渲染**：先 `<pre>` + Diff，P3.2 再考虑嵌入 Control UI 的 Markdown/终端组件。
5. **真实模型可选**：CI/回归用 Fake agent 保证确定性；真实 Pi 作为手动验收（opt-in）。
6. **Repair 仍是一轮**：`iteration=1`；多轮统计留到 L4。

---

## 7. 验收与证据

- **浏览器 E2E（核心）**：从空库开始，Playwright 驱动真实 Control UI，完成整条链路；
  断言 `tested_pass`、最终 Diff、测试输出可见。
- **Sidecar/Worker 测试**：只执行已批准对象；拒绝/过期/租约冲突；tick 幂等。
- **CI**：根测试 + 插件 build/validate；浏览器 E2E 作为本地/发布前证据（暂不塞进 CI）。
- **证据产物**：截图 + `cycle` JSON + 测试输出摘要。

## 8. 风险与开放问题

| 风险 | 处理 |
| --- | --- |
| 真实 Pi 的不确定性/成本 | Fake 用于 CI；真实 Pi 手动跑，记录模型与耗时 |
| Worker 崩溃/租约 | 复用现有 lease + `recover`/`reconcile`；tick 幂等 |
| Docker 在 Windows/CI 的差异 | 沿用 v1.0 的 `sandbox-real` 约束 |
| 事件传输 | 先轮询；`feature.watch` 需要插件 service，Phase 2 评估 |
| 日志体积/敏感信息 | 复用现有证据截断与脱敏；UI 只读摘要 |

---

## 9. 明确不做

- 多用户、公网、远程访问。
- 自动 approve / 自动 apply / 自动 merge。
- 新的沙箱 profile 或新的执行后端。
- L4 多轮可靠性统计。
- 重写 OpenClaw 的聊天、通知、桌面或会话层。
