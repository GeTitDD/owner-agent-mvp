# 项目库是视图不是存储，快照不可变，删项目连删快照

需要围绕单个项目导出知识并发出去，并且每个项目有一份可记版本号的知识库。仓库里已经存在三种「版本」：画像与图谱各有 `revision` 分表，知识条目有不可变的 `personal_revisions`。再加一层「项目知识库」的实体存储，就会让同一条事实出现第四份副本——那正是 ADR-0002 与本轮清理一直在消减的东西。

所以项目库定义为**视图**：本项目经验、所属领域的知识、由本项目升上去的知识、画像与图谱的聚合。它不产生新事实，只在发布时被拍成一个快照。

- **快照以 JSON 为准**，HTML 与图片由它渲染。渲染物按快照缓存，重发不重渲：同一份输入应当得到同一份输出。
- **草稿没有版本号**。一个项目只保留一份草稿，重新生成即覆盖；发布时才分配 v1、v2……，快照此后不可修改。版本号回答的是「我发过几版」，草稿占号会让对方拿到的第一版叫 v4 且无从解释。
- **两个动作**：导出只生成文件到本地固定目录；发布等于「生成快照 + 导出 + 发飞书」。保留导出这个出口，是为了能在发出去之前自己读一遍。
- **内容分两节**：已验证的知识与有证据的经验，以及「观察中」的待验证条目。藏起来会让对方以为项目只有这么多，混在一起又会把观察当成结论。
- **画像与图谱要标明新鲜度**：基于哪个提交、生成于何时。过期内容仍导出，但不标注就等于让收件人把三个月前的画像当现状。
- **删除项目连带删除其快照与本地导出目录**，删除前逐条列出路径。这一条与「保留归档」相反：快照是发出去过的东西，但用户明确选择连坐，接受由此产生的后果。

## Consequences

- 已发飞书卡片里的本地路径在项目删除后会失效。首版只发文本卡片，因此这条后果是明确的、可预期的，而不是意外。
- 快照不可变意味着自动 diff 需要保留上一版；发布时可选写一句说明，事实由 diff 给，意图由人给。
- 「领域知识怎么进某个项目的库」需要一个明确规则：属于该项目的领域，加上由该项目升上去的。只取后者会让新项目一片空白，全取又会让库变成整个领域的镜像。
- 首版只发文本卡片：飞书 webhook 目前只支持 `msg_type=text`，发图需要先上传拿 `image_key`，那是唯一有技术风险的环节，不与主链路一起做。
- 旧的画像与图谱修订不迁入项目库。它们当时没有「结论加证据引用」的形状，硬转会把两种结构混在一起；需要溯源时仍可查原表。
