# 执行记录、经验与知识分三层，证据是唯一通行证

一条 `experience/v1` 记录里同时装着两样东西：一次执行的事实（改了哪个文件、测试过没过、证据指向哪）和一句可以复用的教训（「retry 退避上限调到 30s 会让集成测试超时」）。前者按运行次数增长，后者按「值得记住的结论」增长，混用一个词之后，界面必然变成一堆长得一样的记录。真实数据佐证：库里 40 条经验里 30 条是种子数据、5 条从非终态采集、40 条全部指向已删除的项目，而真正可复用的结论只有 2 条。所以拆成三层，各层有自己的生命周期、作用域与去重键。

```text
执行记录  ──提炼──▶  经验  ──收敛──▶  知识
（原料，项目级）      （教训，项目级→域级）    （规则，域级）
```

- **执行记录**：owner store 里已终态的 sandbox run、job、patch 的只读投影，不物化成表，因此不会出现「项目删了、记录还在」的孤儿。按 ADR-0002，事实只存在 owner store 一处。
- **经验**：从执行记录里提炼出的「现象 → 机制 → 对策」三元组，带证据引用。默认项目级；另一个项目复现同一现象后升为域级。
- **知识**：由一条或多条经验收敛出的域级通用规则，必须写明适用范围与例外。不能从执行记录直接提炼。

四条规则把这套结构撑住：证据必须能追到具体的执行记录，追不到的只能标「推断」，永远不升为已验证；去重键取「提炼时产出的规范化现象短句 + 作用域」，而不是整段文本的哈希；域级经验覆盖项目级，同级冲突标 `disputed` 等人裁决，不自动裁决；升为已验证由人点一下，系统只在另一个项目复现同一现象时打「已复现」标记，不自动升。

## Consequences

- 知识页从「四种类型平铺」变成「候选队列 + 经验 + 知识」；执行记录移去专注页的工程区，按项目看最近 100 条。经验不再以条数形态出现在知识页——它本来就不是按条读的东西。
- 提炼从「拼 40 个任务标题」改为「执行记录 + 它引用的证据」（失败日志、diff 摘要、测试退出码）。对话记录不参与提炼：对话是问过什么，不等于做过什么。
- 提炼按需触发；同一类现象积到第 3 次时界面主动提议。自动提炼会为一次偶发失败编出教训，完全手动又永远想不起来点。
- 模型读完整三元组加证据去检索，人读一句话结论加证据条数。本地几百条的量级用结构化过滤加关键词匹配即可，不引入向量库。
- 迁移时 40 条孤儿记录导出为 JSON 存档后删除。删数据可以回滚，但图纸错了会一直错下去，所以先改定义再动数据。
