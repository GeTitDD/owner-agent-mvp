## 0. 结论（TL;DR）

1. **OpenClaw 已经实现了 v1.1 需要的整个客户端层**：常驻 Gateway、WebSocket 协议、Control UI（会话/审批/设置）、浏览器与 macOS 推送、Tauri 桌面壳。这些都不应该由我们重写。
2. **建议采用方案 A：官方 Feature Plugin**。OpenClaw 跑原版、Control UI 跑原版，我们只交付一个 npm 插件包（工具 + 原生页面 + 内联视图）和一个 Owner 常驻 sidecar。
3. **Owner Agent v1.0 仍是唯一的任务执行与审批权威**：插件只是"展示 + 提交 + 转发"，审批必须携带 Owner 冻结的 64-hex 哈希，模型侧没有任何审批工具。
4. **不建议 Fork 客户端**：Control UI 约 3.4k 个非测试 TS/TSX/CSS 文件、SolidJS 2.0 RC、22 种语言的翻译记忆；上游 567 个 tag、每周 2–4 个版本。Fork 的初版工作量约为方案 A 的 4–5 倍，且每月都要跟版。
5. **最小 PoC 约 6 人日**，只做一条链路：Control UI 里提交 code-patch Job → 审阅 → apply → sandbox → `tested_pass`。PoC 不碰 v1.0 的状态机、哈希协议与测试入口。

## 1. 背景与目标

### 1.1 为什么要调整

v1.0 已经把"任务—补丁—测试—修复"做成可审计的闭环，但客户端层一直是自建的小型 Web UI（`web/`，6 个文件、49 KB）与 Electron 壳（3 个文件）。对照 OpenClaw：

| 客户端能力 | Owner 现状 | OpenClaw 现状 |
| --- | --- | --- |
| 会话与 transcript | 无 | 完整（Markdown、图片、工具活动、分支、压缩） |
| 审批 UI 与通知 | 只有 CLI + JSON | Web Push + macOS 原生 + `/approve/<id>` + 静默时段/分级 |
| 桌面客户端 | Electron 玩具壳 | macOS 原生、Windows Hub（WinUI）、Tauri v2 |
| 设置、诊断、多设备 | 无 | 完整 |
| 实时流式与重连 | 无 | WS + 事件 + 恢复/重放语义 |

继续自建等于在成熟实现之上重写一遍，违背"禁止在有成熟实现时自行重写"的原则。

### 1.2 目标（v1.1）

- 用 OpenClaw 作为**唯一的交互与会话层**（浏览器 + 桌面）。
- Owner Agent 继续作为**唯一的任务执行与审批权威**（Job/Proposal/Sandbox/Repair/知识）。
- 优先原样复用 OpenClaw 代码；必须新写的只有两者之间的适配层。
- 保持 v1.0 的全部安全不变量不变。

### 1.3 非目标

- 不把 Owner 的领域模型（Job 状态机、补丁协议、沙箱、修复循环）迁进 OpenClaw。
- 不让 OpenClaw 的 exec/写文件工具代替 Owner 执行项目变更。
- 不在本阶段做多用户、多租户、移动端、公网暴露。

## 4. 依赖与许可证分析

### 4.1 许可证

| 组件 | 许可证 | 义务 | 风险 |
| --- | --- | --- | --- |
| OpenClaw 本体（GitHub + npm） | MIT | 分发时保留版权与许可文本 | 无 copyleft |
| 内嵌第三方（SQLite 公有领域、Pi/pi-mono MIT、GitHub Octicons MIT、Hermes Agent MIT） | PD / MIT | 保留 notice | 低 |
| 我们新增的插件与 sidecar | 建议 MIT | 与主仓库一致 | 无 |
| Control UI 依赖（SolidJS 2.0 RC、Vite 8、CodeMirror 等） | MIT/Apache-2.0 等 | 随 `openclaw` 包分发，不单独引入 | 预发布框架，升级需跟随上游 |

结论：**无许可证阻塞**。若未来分发桌面安装包，需要附带 `openclaw` 的 `LICENSE` 与 `THIRD_PARTY_NOTICES.md`。

### 4.2 运行时与供应链

| 项 | 影响 | 应对 |
| --- | --- | --- |
| 宿主要求 Node >= 24.16 | Owner 现为 >=22.13（CI 用 22） | **进程分离**：OpenClaw 用 Node 24；Owner sidecar 保持 Node 22，互不升级 |
| `@openclaw/gateway-*` 要求 >=22.19 | 若方案 B 引入，需把 engines 提到 >=22.19 | CI 用 `22.x` 最新即可；显式声明 |
| `openclaw` 打包 262 MiB / 68 依赖 | 安装体积、启动时间、审计面 | 作为**外部安装**，不进我们的依赖树；PoC 用全局/独立目录 |
| 插件 API 全部 experimental | 升级可能破坏 | 锁死 `2026.11.1`，CI 增加"插件兼容性"用例，升级单独 PR |
| 每周 2–4 个 release / 567 tags | 跟版成本高 | 只用精确版本 + lockfile；不追 beta |
| 插件后端由 Gateway 进程加载 | 插件代码拥有宿主进程权限 | 插件保持"薄"：无密钥、无业务逻辑、只做转发（§6） |

## 5. 集成方案

### 方案 A：官方 Feature Plugin（推荐）

```
┌─────────────────────────────── OpenClaw（原版，Node 24）───────────────────────────────┐
│ Gateway :18789                                                                          │
│  ├─ Control UI（原版 SPA）── 会话 / transcript / 设置 / 审批页 / 通知                    │
│  ├─ 会话与会话存储（原版）                                                               │
│  ├─ 通知：浏览器 Web Push + macOS 原生（原版）                                           │
│  └─ 插件 "owner-agent"（我们交付，npm 包）                                               │
│       ├─ Gateway RPC：owner.status / owner.jobs.* / owner.patches.* / owner.repairs.*    │
│       ├─ 工具：owner_status、owner_jobs_list、owner_job_submit（**无审批工具**）          │
│       ├─ 原生页面：Owner（任务 / 提案 / 修复周期）                                         │
│       ├─ 内联视图：审批卡片、修复周期卡片                                                 │
│       └─ 审批：plugin.approval.request（仅展示/收集，哈希由 sidecar 生成）                  │
└───────────────────────────────────────┬─────────────────────────────────────────────────┘
                                        │ loopback HTTP + 一次性 bearer（127.0.0.1）
┌───────────────────────────────────────▼─────────────────────────────────────────────────┐
│ Owner sidecar（本仓库，Node 22）                                                          │
│  OwnerStore（SQLite，唯一权威） · PatchCodingWorker · SandboxRunner · RepairService        │
│  新增：`ownerctl serve` → /owner/v1/*（读 + 提交 + 审批；审批必须带 64-hex 哈希）           │
└─────────────────────────────────────────────────────────────────────────────────────────┘
```

**复用面**：Gateway、Control UI、会话、通知、审批管道、桌面壳、Markdown/终端/编辑器全部原样。
**新增代码**（估算）：

| 模块 | 估算 |
| --- | --- |
| Owner sidecar HTTP 适配层（鉴权、路由、错误映射、审计 origin） | 500–800 行 |
| 插件后端（manifest、RPC、工具、sidecar 客户端） | 800–1,200 行 TS |
| 插件原生页面 + 内联视图（Solid 或原生 DOM） | 600–1,000 行 |
| 测试（契约、负向、E2E） | 400–600 行 |
| 文档与打包 | — |

**工作量**：PoC 6–8 人日；可用版本 3–4 周（含真机验收）。

**风险与缓解**：

| 风险 | 缓解 |
| --- | --- |
| 插件 API 实验性 | 锁版本；兼容性测试；升级单独 PR |
| 插件拥有 Gateway 进程权限 | 薄插件；无密钥；sidecar 二次鉴权 |
| OpenClaw 自带工具可改仓库 | Owner 会话使用受限工具策略（deny exec/write/edit）；见 §6 |
| UI 品牌仍是 OpenClaw | 插件页自带标题/图标；不追求整站换肤 |
| 宿主 Node 24 | 进程分离；Owner 不升级 Node |

### 方案 B：Fork 客户端（不推荐）

```
Fork Control UI（ui/）→ 换品牌、删功能、改路由
   ├─ 复用 @openclaw/gateway-protocol + @openclaw/gateway-client
   ├─ 自建审批页 / 通知 service worker / VAPID 处理
   ├─ 自建 Owner 页面（任务、提案、修复）
   └─ Fork Tauri 壳 / macOS App（可选）
```

**复用面**：协议包；可移植部分 UI 组件与设计 token。
**新增/维护代码**：整个 SPA 的所有权（约 3.4k 非测试文件、23.8 MB 源码）、构建设计、i18n、通知、桌面打包与签名。

**工作量**：6–10 周达到可用；之后每月 1–2 人日跟版（上游每周 2–4 个 release）。

**风险**：

| 风险 | 说明 |
| --- | --- |
| 上游漂移 | 协议 wire version、插件 host API、Control UI 内部结构都可能变 |
| 预发布框架 | SolidJS 2.0 RC、Vite 8，升级路径不由我们控制 |
| 功能回退 | 会话、附件、压缩、分支、a11y、i18n 任何一处漏移植都是回归 |
| 通知 | 需要自己实现 VAPID、订阅生命周期、权限降级、静默时段 |
| 安全 | 自建审批页要重新证明 scope 校验、first-answer-wins、防重放 |
| 成本 | 与收益不成比例：我们差异化的是 Owner 权威，不是聊天 UI |

### 5.1 工作量比较

假设：1 名熟悉 Node/TS 的开发者；不含产品设计与 Owner 评审时间；两者都需要同一套 Owner sidecar（约 5 人日，已从增量中剔除）。

| 维度 | 方案 A：官方插件 | 方案 B：Fork 客户端 |
| --- | --- | --- |
| 初版（PoC） | **6–8 人日** | 15–20 人日（仅骨架 + 一条链路） |
| 可用版本 | **3–4 周** | **6–10 周** |
| 会话/transcript/附件 | 0（原样） | 需移植并回归 |
| 审批 UI | 0（复用审批管道） | 2–3 周 |
| 通知（Web + macOS） | 0（原样） | 1–2 周 |
| 桌面 | 0（官方安装包） | 2–4 周（Tauri/签名） |
| 升级成本 | 改一个插件包 | 合并整个 SPA + 协议 |
| 上游破坏面 | 插件 API（小） | UI 内部 + 协议（大） |
| 可回滚性 | 停用插件即可 | 回退整个客户端 |
| 品牌控制 | 中（宿主品牌） | 高 |
| 结论 | **推荐** | 仅当"必须整站换肤"时才考虑 |

### 5.2 备选：A0（零插件，MCP only）

Owner 暴露一个 MCP server，OpenClaw 通过 `mcp.servers` 调用 `<server>__<tool>`。
优点：0.5–1 人日即可验证工具链；缺点：没有原生页面与审批卡片，审批仍要回到 CLI/自建页面。
**定位**：方案 A 的**第 0 步去风险实验**，不是最终形态。

## 6. 安全边界：Owner 权威不可绕过

### 6.1 权威划分

| 领域 | 权威 | 说明 |
| --- | --- | --- |
| 会话、消息、UI、通知、设备配对 | OpenClaw | 可重建、可丢失 |
| 项目、任务、Job、补丁、沙箱、修复周期、知识 | **Owner** | 不可被 OpenClaw 直接写 |
| 审批决定 | **Owner**（哈希绑定，first-answer-wins） | OpenClaw 只负责收集与展示 |

### 6.2 硬规则

- **R1 模型没有审批工具**：插件只注册 `owner_status` / `owner_jobs_list` / `owner_job_submit`。审批只能由操作员在原生页面触发。
- **R2 审批必须带哈希**：sidecar 审批接口要求 `X-Owner-Approval-Hash`，值来自 Owner 冻结的 cycle/proposal 记录（64-hex），模型无法构造。
- **R3 双向 first-answer-wins**：OpenClaw 审批记录与 Owner 决策都以第一次回答为准；重复/竞态回答返回既有结果，不产生第二次状态迁移。
- **R4 插件是薄客户端**：不保存密钥、不缓存业务状态、不直接读写 SQLite；所有写入经 sidecar。
- **R5 项目写入只走 Owner**：Owner 会话的 OpenClaw 工具策略必须 deny `exec`、`process`、`write`、`edit`、`apply_patch` 及项目目录的浏览器自动化。
- **R6 测试只在 Owner 沙箱执行**：OpenClaw 的 sandbox/exec 不得运行项目测试，避免出现第二套"通过"证据。
- **R7 审计来源**：sidecar 在每次变更时记录 `origin = { gatewayInstanceId, sessionKey, runId, operatorId }` 到 Owner 事件流（不改表结构）。
- **R8 故障隔离**：OpenClaw 停止/崩溃不得让 Owner 进入半提交状态；sidecar 的写操作保持 v1.0 的单事务语义。

### 6.3 威胁与验证

| 威胁 | 攻击路径 | 防护 | PoC 负向用例 |
| --- | --- | --- | --- |
| 模型自批 | 诱导模型调用"批准" | 不存在该工具（R1）；即使直接请求 RPC，也缺 scope 与哈希 | 工具调用 `owner_*approve` → 404 |
| 伪造哈希 | 模型编造 64-hex | sidecar 与冻结记录比对，不匹配 409 | 错误哈希 → 409 |
| 重放 | 重复提交同一审批 | 幂等键 + first-answer-wins | 二次审批 → duplicate |
| 越权写仓库 | 用 OpenClaw exec 改文件 | 工具策略 deny + Owner worktree 隔离 | `exec` 在 Owner 会话不可用 |
| token 泄漏 | 插件日志/浏览器 | token 只在 sidecar 文件（0600）与插件内存；不出现在页面 | 页面无 token；日志无 token |
| 并发双写 | 两路同时审批 | Owner 单事务 + 唯一约束 | 并发审批只成功一次 |
| 插件供应链 | 恶意插件 | 只装自有包；`plugins.allow` 白名单；审阅 manifest | 未列入 allow 时拒绝加载 |

### 6.4 与 OpenClaw 既有审批的关系

OpenClaw 的 exec 审批与 plugin 审批共用 durable approval registry，但按 `kind` 区分（`exec` / `plugin` / `system-agent`）。Owner 审批使用 `kind: plugin`：

1. sidecar 创建修复周期后，插件调用 `plugin.approval.request`，payload 只含脱敏摘要与 `urlPath`；
2. 通知走 OpenClaw 的推送管道（通用文案，不含命令/路径）；
3. 操作员在 `/approve/<id>` 确认 → 插件把该审批 id 映射到 Owner cycle id，并带上 R2 的哈希调用 sidecar；
4. sidecar 返回最终状态；插件把结果写回审批记录；
5. 任一侧已终止则另一边返回既有结果（R3）。

这避免了两套"批准"语义互相漂移，也不需要我们重写通知与收件箱。

## 7. 最小 PoC 计划

### 7.1 目标（只证明一件事）

在 **原版 Control UI** 内完成一次 Owner 的 code-patch 闭环，且**模型无法审批**、**Owner 权威不变**。

### 7.2 范围

| 步骤 | 交付物 | 退出判据 | 估算 |
| --- | --- | --- | --- |
| P0 环境钉版 | `openclaw@2026.11.1`（Node 24）+ Owner（Node 22）；记录协议/插件 API 版本 | `openclaw gateway` 起来，Control UI 可访问 | 0.5 天 |
| P1 Owner sidecar | `ownerctl serve`：`/owner/v1/health`、`/summary`、`/jobs`、`/jobs/:id`、`/patches/:id`、`/repair-cycles/:id`；`POST /jobs`、`POST /patches/:id/approve`（哈希）、`POST /repair-cycles/:id/approve`（哈希） | 单测 + 契约测试；无 token 401；错哈希 409 | 2 天 |
| P2 插件骨架 | `openclaw.plugin.json` + `definePluginEntry`；3 个只读/提交工具；1 个原生页面；`owner.*` RPC | `plugins inspect --runtime` 通过；页面出现在侧边栏 | 2 天 |
| P3 端到端 | 提交 Job → 生成提案 → 页面审批 → apply → sandbox → `tested_pass` | 全程不离开浏览器；Owner 事件含 origin | 1 天 |
| P4 负向与文档 | §6.3 的负向用例；安装/回滚说明；证据 JSON | 全部负向用例符合预期 | 0.5 天 |

合计 **6 人日**（不含真实模型费用与 Owner 评审时间）。

### 7.3 验收标准（可证伪）

- **C1** Control UI 内完成 `code-patch` 的提交→审批→apply→sandbox→`tested_pass`。
- **C2** 模型侧无任何审批路径；直接调用审批 RPC 被拒绝（有测试输出）。
- **C3** Owner `events` 中出现 `origin`（gateway/session/run/operator）。
- **C4** 强制杀掉 OpenClaw 后，Owner 无半提交状态；重启后页面能恢复读取。
- **C5** v1.0 不变量不变：哈希链、单事务审批、scope 校验、复测快照测试 hash 一致；`npm test` 全绿。
- **C6** 版本钉死：`openclaw` 精确版本 + lockfile；升级需另开 PR 跑兼容性用例。

### 7.4 PoC 不做

- 不 Fork/改造 Control UI 与桌面壳。
- 不做多用户、远程访问、公网、移动端。
- 不新增 TestProfile、不改 Owner 数据库结构（`origin` 只进事件）。
- 不做 L4（多轮真实模型统计）、不改 v1.0 状态机。
- 不发布到 ClawHub/npm（先本地 `plugins install .`）。
