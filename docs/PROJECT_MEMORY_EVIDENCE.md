# 决策是否真的存在于会话原文里：一次取样验证

在写「项目记忆」的 spec 之前，先验证一个前提：**用户做过的决策，是否真的留在其他 Agent 的会话原文中**。如果不成立，那条线就该改成「从提交信息提炼，会话只作补充」。

## 方法

```text
来源    Codex 会话 957 个（cwd=D:\nautilus_trader）+ 618 个（cwd=D:\Codexproject）
        Claude Code 会话 61 个（D--nautilus-sys 37、D--Codexproject-nautilus-sys-modular 24 等）
取样    只取 user 角色的原话；按决策线索词过滤（不用/删掉/改成/换成/先不…）
去重    按正文 sha1 前 12 位去重（会话 fork 会让同一句话出现多次）
过滤    排除环境上下文、图片标签，以及 Codex 注入的 system history
```

关键字扫描，没有语义模型参与。这是限制，也是它可信的地方：凡是命中的，原文里确实有那句话。

## 结果

```text
去重后决策原话            119 条
含明确「放弃 / 替换」动作    97 条（82%）
自带理由                    13 条（11%）
动作与理由都有              10 条（8%）
```

同一句话在 fork 出的会话里重复 4–8 次；Codex 还会把历史以 `The following is the Codex agent history...` 注入为 user 消息——第一版扫描就把它当成了用户原话。

## 三个样本

**信息完整的一类**

> 给 AI 漫画单独做一个 flow，这个 flow 关心的是每个画格的具体画面要用什么参考以及什么约束来生成。而不用关心画页和后期制作的比如对话气泡。〔…〕给 flow 做成一个随时可关闭的弹窗式的东西。

现象（工具多、空间挤）、机制（画页与单格混在一处）、对策（弹窗 flow）三层都在，理由也在。

**只有对策的一类**

> 把我们官方提供的 LLM 的 API 换成我本机的环境变量里的 opencode 的 API，默认提供 DeepSeek Flash 4.1

对策极具体，但为什么换一个字没有。是为成本、为可控、还是为速度，只能猜。

**助手补全的一类**

> 优化进入世界的部分可以先不用继续做，先把其他的做了

助手紧接着把「先不做」展开成四项（图片传输、入口数据缓存、界面延迟加载、手机测速）。只取用户那句，会丢掉一半范围。

## 结论

**决策确实在原文里，但形态是「祈使句 + 变更对象」，理由是稀缺品。**

1. **决策条目要成对取**：用户原话加紧随的助手确认。82% 有动作、只有 11% 有理由，而助手那一侧几乎总把模糊指令翻成具体范围；只取用户那句，信息量大约差一半。
2. **「为什么」要在确认时问人，不要指望从原文挖。** 11% 的命中率意味着绝大多数决策会缺机制这一段。而在人点确认的那一刻，理由还在脑子里；两周后才没有。
3. **去重与注入过滤是硬要求。** 按内容哈希去重，并排除 system 注入的历史块，否则库里会存同一条决策的八个副本。

## 一个范围上的意外

这 119 条里没有一条属于本仓库。本项目的工作发生在 OpenCode 里，会话存在 `opencode.db`（约 5.5 GB），而 Codex 与 Claude Code 里是 nautilus_trader、Codexproject 那些项目。

所以「先接 Codex + Claude Code」这个顺序针对 nautilus 是对的，针对本仓库是空的。若要看本项目自己的决策，OpenCode 必须纳入——那是当初被排到最后的一项。

## 对 spec 的影响

- 采集范围：Codex 与 Claude Code 先行，OpenCode 不能永久缺席。
- 条目形状：`用户指令 + 助手确认 + 人补的理由`，三者缺一不可。
- 摄入管道：内容哈希去重与注入块过滤写在第一层，不是后期清理。
- 确认界面：理由如果是选填，实际会一直空着；至少要给一个「为什么」的输入位，并在界面上显示这条缺不缺理由。
