# 真实项目体验实验：能记住，但还不能顺畅复用

日期：2026-11-27（Asia/Shanghai）。这是实际使用评估，**核心经验复用旅程未通过**；不是功能全部完成的交付声明。

## 实验材料与边界

使用本机两个真实 Git 项目：`owner-agent-mvp`（HEAD `65cdbae`）与桃花坞 `AI-Novel-Writing-Assistant`（HEAD `76c8d514`）。
两者都有已有未提交工作，应用只读登记项目。实验结束时核对两者 HEAD、已有未暂存差异，均与基线一致；桃花坞 Git 状态也逐字一致。
本轮没有修改业务代码。Owner 仓库新增的报告、截图与账本是有意保存的验收产物，未提交、未推送。

选用桃花坞真实提交 `b01ee7c037a2ea09557d3d3fd9aa40af2a6f1202`：
`scripts/actor-sft/application/production-orchestration-service.mjs` 修复多个并发任务的状态读改写互相覆盖；
`saveTask` 与 `reconcile` 的短状态写入统一排队，任务执行仍并行；只在 drain 首次对账恢复中断任务。
这里只阅读实际提交，**没有重跑桃花坞测试，也不据此认定跨进程互斥已经解决**。

使用全新隔离 Owner/Knowledge SQLite，没有复制演示项目、经验、任务或假执行记录。
目录选择器由实验宿主返回这两个真实路径；登记、界面、IPC、存储、模型 SDK 与工作台均使用当前代码。
系统目录选择器本身不在验收范围。工作台经现有 `openFull` IPC 打开同一进程自带服务；未证明普通用户能从桌面快速发现该入口。
Gateway 指向不可连接的本机端口 1，未访问个人 OpenClaw。

用户明确授权最多三次真实模型调用。实际通过本机 Pi 凭据和已安装 SDK 调用 `deepseek/deepseek-flash` **3 次**，每次一轮、无工具后续调用。
隔离宿主在 `ModelRuntime.streamSimple` 第四次调用前拒绝；没有替代或伪造模型答复。未显示或复制凭据内容。
三次分别用于提交摘要分析、同项目新会话复用、另一项目请求复用。第三次发生在知识仍属项目级时，**其无结果不能单独算跨项目权限错误**。
改成领域共享后没有再调用模型，以守住预算。

## 优先缺口与建议

### R01 · P0：同项目“保存后免重复解释”未接通

已接受知识确实存在，开同项目新会话后仍要重新粘贴。第二次真实请求只有问题、项目与技能等上下文，没有经验正文或条目 ID；模型如实拒绝编造。
源码对应 `desktop/main.cjs:3376` 聊天处理与 `src/pi-chat.mjs:189` 提示构建；`main.cjs:4242` 的经验检索 IPC 没有进入这条普通提问路径。

建议先统一只读召回入口，让普通提问取得当前项目/领域的 Lesson 与 Knowledge；区分正式知识、推断、争议和已取代状态，附稳定条目 ID、修订、来源与命中理由。
未命中明确说明，不把通用模型知识冒充本地经验，也不把引用自动复制成另一个项目的记忆。

验收：A 保存并接受 → A 新会话提问无需复述；随后明确设为领域共享 → B 同领域可引用；项目专用仍隔离；重启保持；真实请求与可见引用能对应。

### R02 · P0：经验正文截断关键边界，审核无法补全

原文 160 字之后的“跨进程还需独立互斥或 CAS，不能把 Promise 队列当跨进程锁”仍在证据中，却没有进入 Lesson 现象与最终知识 r1 正文。
机制、对策为空，候选照样能接受。这里不是原始灵感彻底丢失，而是**正式正文不完整**，不能只靠读者自己翻证据修正理解。
源码对应 `src/idea-lesson.mjs:51` 的短句映射与空字段、`src/knowledge-loop/promotion.mjs:54` 的正文合成。

建议将标题与正文分开；在第一次确认前提供现象、机制、对策、适用边界、证据的可审阅草稿，不从任意灵感凭空推断机制。
长内容必须显式说明保留范围；不能把标题截断结果当作完整正文。允许人工补全或取消，不静默升级验证状态。

验收：复用本实验的长原文，正式知识正文和后续引用都包含进程内/跨进程边界；修改前后可追修订；不完整草稿有明确提示与补全入口。

### R03 · P1：范围选择和人工确认过于绕路

流内只有“提升为 Lesson → 提升为候选 → 接受”，三次动作；没有在审核卡选择项目/领域，也不能改写正文。
工作台能补救：实验将同一知识修订为 `scope=domain`、`layer=applied`、`domains=[software-engineering]`，没有新造第二条正式知识。
原始 Lesson 仍是空机制/空对策，工作台 Lesson 页又提示去流内编辑，但实际流内没有该入口。

建议收敛为约定的两次确认：先确认结构化经验，再在同一张卡确认知识正文及范围；准备候选作为内部状态，不再要求额外点击。
保留工作台深度修订能力，桌面提供直达当前条目的明确入口。

### R04 · P0：`/经验` 不检索已接受的领域知识

工作台 r2 保存后，Owner 的项目库计到领域知识 1 条，同一个关键词 `/经验 并发状态` 仍报告没有匹配。
这是不同入口查询对象不一致，不能再归因于原知识是项目专用。
对应 `desktop/shell-compose.cjs:1300` 只组合 Lesson 列表与待审候选；与 ADR-0015 约定的 Lesson / Knowledge 查询不一致。

建议显式命令与隐式召回复用同一查询服务，结果标明“经验/知识”、状态、来源、范围、命中理由；已接受条目不继续以未处理候选动作误导用户。

验收：本实验 r2 在 Owner 中 `/经验 并发状态` 能命中，并指回同一知识 ID / r2；项目专用知识不越界；关键词为空给计数与少量近期结果。

### R05 · P1：关联方法只带项目路径，未带选中的经验

`@@ 关联项目` 确实读到“经验 1 条”，但生成物里只有项目名、仓库路径与资料类型，没有经验 ID、正文、证据或可调用的经验检索标识。
对应 `desktop/shell-at-project.cjs:200` 的 `linksToSection`。当前聊天工具也没有知识库读取工具。
生成物已实测；**未额外调用模型来测试关联后回答**，因此不把此项描述成第四次真实模型失败。

建议发送前解析已选资料为受范围约束的只读引用，或提供明确可调用的资料读取能力。显示实际包含几条、引用来源及截断边界；不能以“关联成功”暗示正文已经进入模型上下文。

### R06 · P1：真实项目首步缺少原料引导

仅登记 Git 项目，没有 Owner 执行历史时，自动提炼确实无原料；普通聊天分析也不会变成执行记录。这符合现有设计，不应偷偷把 Git 或聊天伪装成沙箱证据。
但空态只说“已经提炼过的不会重复”，没有告诉新用户需要什么或下一步怎么走。

建议先改清楚空态，说明“本应用已完成的执行记录”与外部提交/人工记录的区别，并直达手动整理路径。
若后续支持选择提交或粘贴日志，应作为**显式证据整理**的独立产品设计：用户选范围、审阅摘要、保留来源，不能后台扫全盘会话，也不能自动标已验证。

## 视觉与交互观察

已打开检查关键实际截图，桌面为 440×640 CSS 像素、工作台 1180×788；含长英文项目名、多行中文、长候选、空态、浅色和深色经验卡。

- 桌面输入框与主操作可用，长路径能换行，基本没有整页横向溢出。
- 长候选正文、证据、来源重复占满多屏，关键适用边界埋在证据中；需要短标题、结构化字段与清晰阅读顺序。
- 工作台长标题把“未验证”徽章挤成竖排（截图 27）；标题与状态应避免互相挤压。
- 生成 prompt 后即时提示条覆盖了关联项目胶囊（截图 19）；截图 23 等提示消失后能读到完整关联区。应检查提示与整个输入区的避让。
- 生成的 prompt 使用横向滚动代码块，长中文不换行；复制产物完整，但屏内审核困难。
- 经验卡曾显示内部状态 `inferred`；项目库回执使用 `domainKnowledge` 等内部键，增加理解负担。
- Lesson 工作台证据只展示 240 字摘要，长路径截在中间，且未提供直达原始灵感的操作；“可追溯”应让用户实际点得到来源。
